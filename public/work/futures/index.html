CoinDCX · Platform isolation

Separating the futures platform from a monolith

A high-impact product needed a narrower change boundary—not the development overhead of the entire platform.

Problem

Futures was a higher-revenue, higher-impact product relative to the platform’s other products. Yet even futures-specific initiatives required considering touchpoints across products because the code lived in a shared Ruby on Rails monolith.

The shared application also imposed a slow feedback loop: the full unit test suite took 40 minutes, and component boot time was 3 minutes. A futures change carried the development overhead of the larger application.

Constraints

The starting point was an existing multi-product Rails application, not an independent service. The extraction had to address the application boundary as well as where the futures platform ran.

Moving infrastructure alone would leave the shared code boundary in place. The work therefore covered code segregation and a separate deployment environment.

Architecture

The application boundary came from extracting the futures code. The infrastructure boundary came from migrating it to a separate Amazon Elastic Kubernetes Service (EKS) cluster. These were complementary parts of the isolation effort.

Decisions

  • Separate the code, not just its hosting. Code segregation addressed the broad application footprint behind futures development, tests, and startup.
  • Give futures a separate cluster. The extracted application also received its own infrastructure boundary rather than remaining in the original shared environment.
  • Accept another environment to operate. Isolation brings a separate application and cluster to maintain; the benefit was a narrower change boundary for a business-critical product.

Execution

I owned planning and implementation of the isolation initiative. My scope included segregating the futures code from the monolith and migrating the extracted platform to the separate EKS cluster.

This was both an application extraction and an infrastructure migration, rather than a cluster move alone.

Impact

Isolation limited the blast radius of futures-specific work and remediated the development-loop pain points. Full unit test runtime fell from 40 to 10 minutes, while component boot time fell from 3 minutes to 25 seconds.

These are development and component-startup improvements, not claims about exchange request latency or production uptime.
